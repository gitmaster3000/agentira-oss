# Workflow Packages — visible, editable, agent-proof workflow code

Date: 2026-09-25 · Status: draft for review · Branch: main-rsi

## 1. Problem

A project's workflow — which checks guard each column, who picks a task up
next, what happens when a merge or review fails, and every prompt an agent
receives — is today spread across application code the user cannot see:

| Piece | Lives in today |
|---|---|
| Column flow, hand-offs, merge/verify/bounce/rejection policy | `templates/workflow/default.yaml` (system-wide, one for every project) |
| Driver decisions (advance, hand back, re-drive, pick agent) | `backend/forge/workflow.py` (~1,200 lines) |
| Column-exit gates | `backend/gates.py` `_TRANSITION_GATES` (Python dict) + `Project.gates_enabled` |
| Implementer prompt (output contract, repo check) | `backend/forge/services.py` |
| Role/hand-off prompts | `templates/workflow/prompts/*.md` (+ per-project text overrides) |
| Column names | hardcoded across the Conductor and the driver |

The Workflow tab shows fragments of this, including a "Starlark" code view that
is generated by the frontend and matches no real file. Users can't tell what
will happen to a task, can't change it per project, and can't write their own
checks. Driving the loop by hand on 2026-09-25 hit 18 defects, most of them in
this hidden logic (see `.superpowers/sdd/2026-09-25-loop-v1/friction.md`).

## 2. Goal

Jira-style workflows with real code behind every transition:

- **Everything is visible**: the rules, the driver logic, the checks and every
  prompt are files the user can read in the Workflow tab.
- **Everything is editable per project** (by project admins/owners), starting
  from a shipped template.
- **Verification is out of agents' reach**: agents can read what will be
  checked but can never change the checks or tamper with where they run.
- **Checks have real access**: git, shell, tests, the task's data — enough to
  actually verify work.
- **The application is only a runtime**: it fires events, runs the package's
  code, applies the decisions it returns, and records evidence.

Non-goals (now): custom columns beyond the global status set (§10, later);
multiple templates in the gallery (only `default@1` ships); a visual rule editor.

## 3. Decisions (agreed 2026-09-25)

1. **Templates, instantiated per project.** The product ships workflow
   templates; only `default` exists for now. A project that enables the
   workflow gets its **own copy** tagged with its origin (`default@1`). The
   project edits only its copy; the template is never changed by a project.
   When a template gets a new version, the Workflow tab shows "based on
   default@1 — v2 available", a diff, and a re-apply action. Nothing changes
   silently.
2. **Columns** come from the global status set (backlog, todo, in_progress,
   review, done). A project may skip or reorder them and change every rule
   around them. Custom columns come later (§10).
3. **Rules code is Python**, run by the project's **daemon**, with git and
   shell access.
4. **Two kinds of exit evidence**: deterministic **checks** (code) run first;
   only if they pass is the **judgment** step dispatched (a reviewer agent's
   run ending in a typed verdict). Optional **human sign-off** per column.
   Neither kind can override the other.

## 4. The package

```
workflow/
  workflow.yaml        # structure: columns, exits, events → hooks, policy knobs
  checks/*.py          # deterministic verification
  hooks/*.py           # driver logic (what happens on each event)
  prompts/*.md         # every prompt, incl. the implementer contract
```

`workflow.yaml` (shape; the ported default in §8 is the reference):

```yaml
template: default@1
columns:
  - name: todo
  - name: in_progress
    enter: {dispatch: {role: implementer, prompt: implementer}}
    exit:
      to: review
      checks: [dod_all_checked, branch_pushed, no_injected_files]
  - name: review
    enter: {dispatch: {role: reviewer, prompt: reviewer}}
    exit:
      to: done
      checks: [branch_pushed, tests_pass]
      review: {role: reviewer, approvals: 1, not_implementer: true}
      human_signoff: false
    on_pass: merge_and_verify       # hook
    on_fail: hand_back              # hook
  - name: done
    enter: {dispatch: {role: documentation, prompt: documentation}}
roles:
  implementer:   {match: [implementer], fallback: any}
  reviewer:      {match: [review, senior], not_implementer: true, fallback: none}
  documentation: {match: [doc, writer], fallback: none}
policy:
  bounce: {max_attempts: 2, window_minutes: 30}
  verify: {command_from: project.verify_cmd, timeout_minutes: 30}
events:
  run_finished: hooks/on_run_finished.py
  merge_finished: hooks/on_merge_finished.py
  tick: hooks/on_tick.py            # retries, stuck-task detection
```

A **check** is a Python file exposing one function:

```python
# checks/tests_pass.py
"""The project's verify command passes on the task branch."""
def check(ctx):
    r = ctx.sh(ctx.project.verify_cmd, cwd=ctx.checkout, timeout=ctx.policy.verify.timeout_s)
    return ctx.result(ok=r.exit_code == 0,
                      reason="tests pass" if r.exit_code == 0 else f"verify failed (exit {r.exit_code})",
                      evidence={"exit_code": r.exit_code, "log_tail": r.tail(200)})
```

A **hook** is a Python file exposing `handle(ctx, event)` that returns
**actions**; it may use git/shell directly in the verification checkout, but
it never writes the board itself:

```python
# hooks/on_run_finished.py
def handle(ctx, event):
    if event.run.outcome != "succeeded":
        return []
    col = ctx.column(event.task.status)
    return [ctx.request_exit(col.exit.to)]     # runtime runs the exit's checks, then review
```

Actions the runtime understands (the complete list; each is audited and
applied by the backend): `request_exit(to)`, `move(to)`, `assign(role|agent)`,
`dispatch(role|agent, prompt, context)`, `hand_back(to_column, reason,
evidence)`, `comment(text)`, `escalate(reason)`, `merge(branch, target,
push, verify)`, `set_branch(branch)`.

## 5. The context API (what checks and hooks can see and do)

`ctx` is the only interface; it is documented in the Workflow tab next to the
code.

- **Data (read-only):** `ctx.task` (fields, DoD, branch, comments), `ctx.runs`
  (the task's runs, outcomes, diffs), `ctx.project` (settings incl.
  `verify_cmd`, repos, default branch), `ctx.reviews` (typed verdicts),
  `ctx.policy` (from workflow.yaml), `ctx.agents` (for role matching).
- **Git:** `ctx.git` bound to the **verification checkout** — `diff(target)`,
  `log()`, `files_changed()`, `merge_into(target)` (temp tree), `push()`.
- **Shell:** `ctx.sh(cmd, cwd, timeout)` → exit code, output tail.
- **Agentira API:** read-only client scoped to the project.
- **Results/actions:** `ctx.result(...)`, the action constructors above.

## 6. Trust boundary

- **Storage.** Packages live in Agentira's database per project, with full
  version history (`workflow_package_versions`: version, files, content hash,
  author, message, created_at). Not in the project repo — an agent with repo
  write access could otherwise rewrite the checks that judge it.
- **Who can change it.** Project admins/owners, in the Workflow tab. There is
  no MCP tool or agent-token API that writes a package; agents can read a
  description of the checks (so they know what will be verified).
- **Where code runs.** Only on the project's daemon — never inside the backend.
  Agentira is also a multi-tenant hosted service; executing customer Python in
  the backend would let any customer run code on the shared server.
- **Verification checkout.** Checks and hooks run in a fresh checkout of the
  **pushed** branch, created by the daemon outside every agent worktree
  (`~/.agentira/verify/<run>/`) and deleted afterwards. The agent's only lever
  is its pushed commits — exactly what is judged.
- **Tamper detection.** Agents run as the same OS user as the daemon, so the
  daemon's cached package copy is not physically out of reach. The backend is
  the source of truth: before every execution the daemon verifies the cached
  files against the version's content hash and re-syncs on mismatch. A local
  edit is never executed.
- **No daemon online.** Checks can't run → the move is held ("waiting for a
  verifier") rather than skipped.

## 7. Runtime (what stays in the application)

The backend becomes an event router + action applier:

1. **Events**: `task_move_requested` (human drag or hook), `run_finished`,
   `review_submitted`, `merge_finished`, `tick` (periodic).
2. For each event, the backend sends the daemon `{package_version, hook or
   checks, context snapshot}`; the daemon executes and returns results/actions.
3. The backend applies actions in order, recording each as a
   `transition_event` with the evidence, the package version and the hook that
   produced it — so every board change is traceable to a line of visible code.
4. **Exit sequence** (`request_exit`): run the exit's checks → if any fail,
   `on_fail` → if all pass and a review is required, dispatch the reviewer →
   on approve (and human sign-off if required) → `on_pass`.
5. **Human drags** go through the same exit sequence; the card shows
   "checking…" until results arrive (seconds for data checks).
6. **Retries are the runtime's job, not luck.** A dispatch refused because an
   agent is at its cap is queued and retried on `tick` (fixes friction #15);
   actions are idempotent per (event, version).

## 8. The default template = today's behaviour, ported

`default@1` reproduces the current system flow (Loop v1 included) as package
files, so enabling packages changes nothing observable on day one:

- Gates `has_dod`, `has_assignee`, `dod_all_checked`, `has_branch_or_pr` →
  `checks/*.py`. The `pr_url_set` gate is dropped for review→done because the
  package merges the branch itself (today this is a silent special case).
- `workflow.py` decisions → `hooks/on_run_finished.py`,
  `hooks/on_merge_finished.py`, `hooks/hand_back.py`, `hooks/on_tick.py`,
  including the fixes found on 2026-09-25: merge the task's work branch, not the
  reviewer's (AP-526); refuse an empty merge (`nothing_to_merge`, friction #12);
  refuse injected files (AP-525); turn-scoped decisions on reused runs (AP-402).
- Daemon merge + verify (`daemon/integrate.py`) → `hooks/merge_and_verify.py`
  using `ctx.git` and `ctx.sh`.
- Every prompt, including the implementer's output contract and repo check
  from `forge/services.py` → `prompts/*.md`.

Parity is proven by running the existing `test_workflow_driver.py` scenarios
against the package runtime.

## 9. Workflow tab

- **Overview**: the columns as a flow; for each column — who is dispatched on
  enter (and the exact prompt), exit checks and review requirements, what
  happens on pass/fail. Every item links to its file.
- **Files**: the package as a file tree with a code viewer (real files, not
  generated text). Editing (admins/owners): save → validate (YAML schema,
  referenced checks/hooks/prompts exist, Python compiles, every column
  reachable) → new version with a message. Invalid packages are refused on
  save, never at runtime.
- **History**: versions with diffs and authors; roll back = new version.
- **Template**: "based on default@1", update available, diff, re-apply.
- **Evidence**: per task and per column, recent check results (pass/fail,
  reason, output tail), reviewer verdicts, and which hook moved the task.

## 10. Later

Custom columns per project (needs per-project statuses on the board and in the
Conductor); a template gallery (workflows + agent teams); mirroring a package
to a repo for review-by-PR; a visual rule editor on top of the same files.

## 11. Delivery phases

1. **Runtime + package format + `default@1` port** with parity tests; the
   daemon executes checks/hooks in a verification checkout; the backend applies
   actions. `workflow.py` / `gates.py` logic is deleted once parity passes.
2. **Workflow tab, read-only**: overview, files, evidence.
3. **Editing**: validation, versions, history, template updates.
4. **Custom columns.**

Each phase is dogfooded on Agentira Platform through the board.

## 12. Risks

- **A broken package stalls a project** → validation on save, and a per-project
  "revert to template" action.
- **Latency on human drags** (daemon round trip) → data checks are small; the
  UI shows progress; no daemon → held, not skipped.
- **A hook with shell access can do damage on the user's machine** → the same
  trust level as the agents the user already runs there; only project
  admins/owners can edit the package; every version is attributed.
- **Porting drifts from today's behaviour** → parity tests before the old code
  is removed.
